Part 2 - The Enterprise Knowledge Graph


In this tutorial we will get familiar with the Enterprise Knowledge Graph (EKG). A knowledge graph is a design pattern for storing, organizing, and accessing interrelated data entities, including their semantic relationships. With knowledge graphs, you can better understand your data and build more intelligent applications.

After finishing this tutorial you will:

  1. 1. Have a basic understanding of the data model (Ontology) of the EKG.

  2. 2. Build more advanced queries to find interesting network patterns.

  3. 3. Gain insight in how the knowledge graph can be helpful to you.

To get started, make sure to use the database rabokgxxx where xxx is the number in your username

:use rabokgxxx

The data model (Ontology)


The Rabobank customers are central to the Enterprise Knowledge Graph. Customers can be either Natural Persons and Organisations, have relationships with other customers, have products and accounts. Transactions take place between accounts (both Rabobank and non-Rabobank).

The graph provides a multi-dimensional 360 degree customer view. Here a few examples of key relations:

  1. - `(:Customer:Person)-[:HAS_ACCOUNT]->(:Account)` - Accounts of a customer (note that the customer is also a Natural Person, nodes can have multiple labels)
  2. - `(:Customer)-[:RELATED_TO]->(:Customer)` - Relationships between customers (ie. family, ownership, ubo, etc.)
  3. - `(:Account)-[:TRANSACTION_WITH_TOTAL]->(:Account)` - Transactions between accounts (aggregated)
We enrich the knowledge graph over time with new node labels and relationships, for more details see the Ontology documentation on Azure DevOps.

Note: To keep queries intuitive, we simplified the RELATED_TO relation in this synthetic version of the graph. We have selected a few types of relations and made them explicit:
  1. - (:Person)-[:HAS_PARENT]->(:Person)
  2. - (:Person)-[:MARRIED_TO]-(:Person)
  3. - (:Person:Organisation)-[:IS_OWNER_OF]->(:Organisation)
  4. - (:Organisation)-[:HAS_AS_UBO]->(:Person)

Prevent getting too many results using LIMIT


The EKG contains data for millions of customers. It can grow up to hundreds of millions of nodes and billions of relations. It is important not to get too many results. If you query to return all customers of the Rabobank, the database will actually try and achieve that. This will take a very long time to process and may cause memory problems.

You can use the LIMIT clause to return a limited number of nodes and relations.

MATCH (c:Customer)
RETURN c.relid AS relid, c.name AS customer_name
ORDER BY customer_name ASC
LIMIT 5

So, what is happening in this query?

  1. 1. If you do not return the variable c itself, but properties of the node, the Neo4j browser shows the result as a table instead of a graph visualisation.

  2. 2. You can use an alias using the AS clause when returning property names (customer_name)

  3. 3. ORDER BY sorts by customer name in ascending order (use DESC for descending)

  4. 4. LIMIT constrains the number of returned rows.

Counting nodes with COUNT


Number of customers in the database:

MATCH (c:Customer) RETURN COUNT(c) AS nr_customers

Number of accounts in the database:

MATCH (a:Account) RETURN COUNT(a) AS nr_accounts

 

Tip: Neo4j maintains a count store for holding count metadata for a number of things, so even if there are millions of nodes in the graph you can count labels like (:Customer) quickly. For more details see Fast counts using the count store.

Counting nodes with DISTINCT


Customers can own more than one account, so if you list customers and their accounts, customer may end up multiple times in the results. See for example the following query:

MATCH p=(c:Customer)-[:HAS_ACCOUNT]->(a:Account)
RETURN c.name, a.iban LIMIT 3

 

The default behavior of COUNT is to count all matching results, including duplicates. To avoid counting duplicates use the DISTINCT keyword.

MATCH (c:Customer)-[:HAS_ACCOUNT]->(:Account)
WITH COUNT(c) AS nr_customers_duplicate, COUNT(DISTINCT c) AS nr_customers_distinct
RETURN nr_customers_duplicate, nr_customers_distinct

Transactions between accounts


In the EKG, transaction relations represent aggregated bookings. They are bi-directional to model incoming and outgoing transactions. The relationship property nr_trx and sum_trx indicate the number of transactions between the accounts and the total sum in EURO value.

In this query we look for customers that received more than 1000 EUR from another account:

MATCH p=(c:Customer)-[:HAS_ACCOUNT]->(a:Account)<-[r:TRANSACTION_WITH_TOTAL]-(:Account)
WHERE r.sum_trx > 1000
RETURN p LIMIT 30

By changing the direction in -[TRANSACTION_WITH_TOTAL]→ you could target customers that sent more than 1000 EUR.

If you don’t care about the direction of the transaction, you can leave out the arrow as follows:

MATCH p=(c:Customer)-[:HAS_ACCOUNT]->(a:Account)-[r:TRANSACTION_WITH_TOTAL]-(:Account)
WHERE r.sum_trx > 1000
RETURN p LIMIT 30

Transactions between customers and their family members


In this query we look for customers that transacted with their children or partners:

MATCH p=(c1:Customer)-[:HAS_ACCOUNT]->(a:Account)-[r:TRANSACTION_WITH_TOTAL]-(:Account)<-[:HAS_ACCOUNT]-(c2:Customer)<-[:IS_PARENT_OF|MARRIED_TO]-(c1)
RETURN p LIMIT 5

Note that the variable c1 is re-used in the pattern. This causes a circular pattern where the inital customer c1 is related to c2.

Supernodes


A super node is any node that happens to have a lot of relationships. How many relationships? Well, millions in the case of the Enterprise Knowledge Graph. For example, the Tax Authority transacts with millions of accounts in the Netherlands. Also, Payment Service Providers or other large companies tend to have lot of relationships.

Let’s see if we can identify the top three nodes with the most incoming connections in our very small synthetic version of the EKG.

MATCH (a1:Account)<-[:TRANSACTION_WITH_TOTAL]-(a2:Account)
WITH a1, count(distinct a2) as in_degree
RETURN a1.iban, in_degree
ORDER BY in_degree
DESC LIMIT 3

This query groups by account and then counts the incoming relationships.

Create network features for Account nodes


Lets add two features to the account nodes that indicate the number of incoming and outgoing connections. We can use them later to filter our queries.

  1. in_degree number of accounts an account received money from
  2. out_degree number of of accounts an account sent money to
// in_degree
MATCH (a1:Account)<-[:TRANSACTION_WITH_TOTAL]-(a2:Account)
WITH a1, COUNT(DISTINCT a2) as in_degree
SET a1.in_degree = in_degree;

// out_degree
MATCH (a1:Account)-[:TRANSACTION_WITH_TOTAL]->(a2:Account)
WITH a1, COUNT(DISTINCT a2) as out_degree
SET a1.out_degree = out_degree;
Tip: Writing features to millions of nodes is often not feasible. The popular plugin APOC has functions available that can write features in batches very efficiently. See: apoc.periodic.iterate

Use network features in queries


Let’s filter to show transactions of accounts that have a large in_degree (supernodes):

MATCH p=(a:Account)-[:TRANSACTION_WITH_TOTAL]-(:Account) WHERE a.in_degree > 30 RETURN p LIMIT 25

Now filter to show transactions of accountsthey have a lower in_degree:

MATCH p=(a:Account)-[:TRANSACTION_WITH_TOTAL]-(:Account) WHERE a.in_degree < 30 RETURN p LIMIT 25

Customer accounts at other banks available via HAS_MATCHED_ACCOUNT relations


Customers may hold accounts at other banks, but this information is not readily available within the Rabobank. We apply Entity Matching to enrich the knowledge graph with HAS_MATCHED_ACCOUNT relations. Based on names from Non-Rabobank accounts as they appear in bookings data, we match customers to their non-Rabobank accounts.

MATCH p1=(:Customer)-[:HAS_MATCHED_ACCOUNT]->(:Account)-[:HAS_NAME_BOOKING]-(:Name)
RETURN p1 LIMIT 10

Scenario - AML transaction pattern 1/2


The following query shows how you could target a transaction pattern where a customer deposits large amounts of cash and additionally sends funds to a foreign account.

MATCH p1=(c:Customer)-[:HAS_ACCOUNT]->(a1:Account)-[:TRANSACTION_WITH_TOTAL]->(a2:Account)
WHERE a1.cash_sum_credit > 1000
AND a2.is_nl = False
RETURN p1

We enriched the Account nodes with two new features to make this pattern possible.

  1. 1. The attribute cash_sum_credit indicates the amount of cash that was deposited to this account.

  2. 2. The flag is_nl can be used to target foreign accounts.

Scenario - AML transaction pattern 2/2


Lets extend the pattern further and include the network of family relations of the customer that deposited cash.

For this scenario we enriched the graph with the :AMLRisk flag to indicate Accounts that are flagged for Money Laundering. (Not an offical label in the EKG Ontology, used here to demonstrate scenario)

MATCH p1=(c:Customer)-[:HAS_ACCOUNT]->(a1:Account)-[:TRANSACTION_WITH_TOTAL]->(a2:Account)
WHERE a1.cash_sum_credit > 1000
AND a2.is_nl = False
OPTIONAL MATCH p2=(c)-[:MARRIED_TO]-(:Customer)-[:HAS_MATCHED_ACCOUNT]->(:Account:AMLRisk)-[:HAS_NAME_BOOKING]-(:Name)
RETURN p1, p2
OPTIONAL MATCH matches patterns against a graph database, just as MATCH does. The difference is that if no matches are found, OPTIONAL MATCH will use a null for missing parts of the pattern. OPTIONAL MATCH could therefore be considered the Cypher equivalent of the outer join in SQL.

Not meant to be a realistic example, but to show how you can find interesting patterns if you enrich the graph with additional features.
